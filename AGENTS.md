# Development and publication

## Development

- Keep the code simple and readable. Prefer the documented behavior of the Microsoft Graph SDK over defensive rules of our own (for example, `@odata.nextLink` is followed as returned when it is https on graph.microsoft.com).
- Run the existing validation before promoting a change: `Invoke-Pester -Path .\tests -Output Detailed` (Pester 5 or later, PowerShell 7.4 or later). A source checkout has no `PackageIntegrity.psd1`: the entry scripts need `-DevelopmentMode` (the tests set it; `tests\support\Import-StoreEngine.ps1` also sets `MBT_ICONS=Ascii` and a temporary log folder).
- Keep private configuration, credentials, tenant data, exported mailbox content (`*.fxs`) and manifests out of commits and release packages.
- Nothing in the automated tests may contact the cloud. Cloud checks are run by the owner with the scripts in `tools\`.
- Never delete or modify existing mailbox items or folders from the lab scripts: imports create only.
- Commits carry only the repository owner's identity. Do not add co-author trailers for assistants or tools.
- Never write a real tenant, application, user or mailbox id, a lab domain or a person's name in a tracked file (code, tests, docs, images, configuration). Use contoso values. A developer's own defaults live in `package\config\MailboxTransfer.config.local.psd1` (git-ignored, read by `Import-MbtConfiguration` after the shipped file); the tests use a synthetic one (`tests\support\Import-StoreEngine.ps1`). `tests\privacy-denylist.local.txt` (git-ignored, optional) lists private terms that a test searches for in the tree. Lab journals and measures stay in an internal folder outside the repository, or in `docs-internal\` (git-ignored).
- Preview public changes and obtain the repository owner's approval before publishing. No remote is configured yet; publication follows the GitHub release procedure (signature with the owner's smart card, timestamp, pull request, release), only with the owner's explicit approval of each step.

## Layout

- `package\` is the runtime package (what the release ZIP holds): `MailboxTransfer.psd1/.psm1`, `Invoke-MailboxTransfer.ps1`, `Start-MailboxTransferConsole.ps1/.cmd`, `module\` (the console, the events of a job, the EML commands), `config\`, `docs\`, `lib\sqlite\` (SQLite for the store, see `THIRD-PARTY-NOTICES.md`), `src\` (`Engine.*.cs`, `Gui.ViewModels.cs`, `Test-PackageIntegrity.ps1`), `product.json`, `PackageIntegrity.psd1` (created at release time, see below). The repository root holds `README.md`, `CHANGELOG.md`, `SECURITY.md` (the standard text, byte for byte: a gate compares it), `LICENSE`, `PROVENANCE.md`, `DOWNLOAD-THE-RELEASE.txt`, `.github\` (CI, CodeQL, attestation), `tests\` and `tools\`.
- The C# engine (`package\src\Engine.*.cs`) is compiled in memory by `Initialize-MbtEngine` (Add-Type), once per process, as in ExchangeLogReport. `Initialize-MbtEngine` first loads SQLite from `lib\sqlite` (native library of the architecture, then the managed assemblies) because `Engine.Store.cs` is part of the same unit. `Engine.Auth.cs` is compiled separately because it needs MSAL.NET.
- The console is `package\Start-MailboxTransferConsole.ps1` with `package\module\MailboxTransfer.Gui*.ps1` (pages, state, run model, jobs, browse card, real and fake engine adapters, scenarios), `package\module\MailboxTransfer.Gui*.xaml` and `package\src\Gui.ViewModels.cs` (compiled by the console, not part of the engine unit). Its tests are `tests\Gui.Logic.Tests.ps1` (no window) and `tests\Gui.Smoke.Tests.ps1` (headless WPF in a single-threaded child pwsh, fake engine); `tools\New-ConsoleScreens.ps1` renders the pages to `out\console-screens\`.
- `tests\` holds Pester tests (`MailboxTransfer.Tests.ps1`, `Store.Tests.ps1`) and C# fixtures (fake HTTP handler, synthetic FastTransfer stream builder, `support\` helpers of the store tests). An in-memory assembly cannot be referenced by a later `Add-Type`: every test file loads the engine through `tests\support\Import-StoreEngine.ps1`, which calls `Initialize-MbtEngine`.
- `tools\` holds lab scripts (`Invoke-Phase0.ps1`, `Grant-LabConsent.ps1`, `Test-FastTransferCorpus.ps1` for the git-ignored corpus `out\fxics-corpus`; `New-LabFxCorpus.ps1` with `LabFxCorpus.Lib.ps1` (offline plan) and `LabFxAuth.cs` (sign-in) creates the real corpus items; `Export-FxCorpusFromStore.ps1` copies streams out of a store; `Test-PstRoundTrip.ps1` writes the corpora to PST and reads them back; `Measure-PstRepair.ps1` repairs a damaged synthetic PST of 2 GB and more and measures the memory; `Test-PstImportLive.ps1` (lab: imports the messages of a PST into the PRIMARY mailbox of the lab user with our own FastTransfer streams, exports them again and lists what Exchange changed with `FxDiff`; silent sign-in only), `Test-ConsoleLive.ps1` (lab, read only: drives the console's real adapter live with the cached token, plans and runs a small export to PST, stops and continues it; run with `pwsh -STA`), `New-MbtAppOnlyLab.ps1` is the optional setup of the app-only sign-in (application, non-exportable certificate, permissions requested, steps for admin consent and Exchange RBAC for Applications; the owner runs it, the tests only run it with `-WhatIf`, see `package\docs\MailboxTransfer-AppOnly.md`), `Invoke-ScanPst.ps1` is an optional developer comparison with Microsoft's SCANPST: the product and the default test suite never depend on Outlook, SCANPST or any external PST tool).

## Signed release (done at release time, with the owner)

- Every PowerShell file of ``package\`` (``.ps1``, ``.psm1``, ``.psd1`` except ``config\``) is signed with Authenticode (the owner's smart card, thumbprint ``0F28E442889F17B5F4D251E8F96E7CC6E2C9C6D6``) and timestamped, then ``package\PackageIntegrity.psd1`` (SHA-256 of every other file, including ``CHANGELOG.md`` and ``SECURITY.md`` of the root) is signed and timestamped last. ``src\Test-PackageIntegrity.ps1`` verifies all of it before any code runs.
- Before signing: ``tools\Get-SigningInventory.ps1 -Normalize`` puts the signed files in the required form (ASCII, CRLF, no BOM) and lists them; every signed path has ``-text`` and ``cr-at-eol`` in ``.gitattributes`` (everything under ``package\`` is ``-text``: the hashes are byte-exact). Edit a signed file after signing and the signature, then the manifest, must be redone.
- After the signatures: ``tools\New-PackageIntegrity.ps1`` writes the manifest, ``tools\New-MailboxTransferPackage.ps1 -Zip`` builds and verifies the release ZIP (``-DevelopmentMode`` is a dry run on an unsigned tree).
- Not created by this repository: branch and tag protections, secret scanning, push protection (GitHub settings, with the owner).
## Documentation

- `README.md`, `package\docs\MailboxTransfer-UserGuide.md` (a beginner can follow it: start here, glossary with where to look, troubleshooting) and `package\docs\MailboxTransfer-Guide.md` (reference). The `.html` of the two guides is built by `tools\Build-Documentation.ps1` (self-contained, images embedded); build it again after any change of a guide or an image.
- `package\docs\images\` is generated by `tools\New-DocumentationImages.ps1` (the real window on the fake engine through `tools\New-ConsoleScreens.ps1`, plus drawings), light and dark, synthetic names only. Run it again when a page of the console changes. Do not edit the PNG files by hand.
- Parts that depend on work in progress (app-only sign-in with a certificate) are marked `TBD` in the guides, so that they are easy to find and fill.
- The CHANGELOG stays short: a few highlights per version, no internal detail.
